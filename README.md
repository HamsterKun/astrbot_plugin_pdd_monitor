# 多多盯价

按关键词监控拼多多搜索结果的最低价。刷新历史最低价时推送至已绑定的会话；群内 @机器人 说「今日行情」查询全部监控项的现价与涨跌。

| 项目     | 值                                                       |
| ------ | ------------------------------------------------------- |
| 插件目录名  | `astrbot_plugin_pdd_monitor`                            |
| 数据目录   | `data/plugin_data/astrbot_plugin_pdd_monitor/`          |
| 依赖     | `playwright`（含 Chromium 内核）、`jieba`、`httpx`、`curl_cffi` |
| AstrBot | ≥ 4.24.2                                                |

---

## 快速上手

四步能跑起来。

1. **装插件**：把 `astrbot_plugin_pdd_monitor` 整个目录放进 AstrBot 的 `data/plugins/`，在面板的插件管理页重载。首次加载自动装依赖；首次取数时自动下载浏览器内核（一百多 MB，只发生一次）。
2. **登录拼多多**：面板 → **插件 → 多多盯价 → 多多盯价登录**，点「开始登录」，用拼多多 App 扫码。成功后画面会盖一张卡片，Cookie 自动写进设置，不用复制粘贴。
3. **加一个关键词**：在群里或私聊发 `/盯价 add 纸巾`。不需要商品链接，插件按这个词去搜。
4. **等推送**：巡检默认 30 分钟一轮，跌破历史最低价时推到绑定的会话。想立刻看现价，发 `/盯价 check` 或 `/盯价 list`。

跑通之后再回头看设置。默认值面向「一台机器、几个关键词、家宽或代理出口」的常见情况，不改也能用很久；真要调的只有「出口代理」（云服务器必填）和「巡检间隔（分钟）」。

面板那一页打不开时（插件页面没出现、出口被限流），退回「登录拼多多 · 手工复制 Cookie」。

## 安装

1. 将 `astrbot_plugin_pdd_monitor` 整个目录放入 AstrBot 的 `data/plugins/`。
2. 在 WebUI 插件管理页重载插件，或重启 AstrBot。首次加载自动安装 `requirements.txt` 中的依赖。
3. 登录拼多多（面板里扫码即可），见「登录拼多多」。
4. 在群内发送 `/盯价 add 纸巾` 验证。

### 浏览器内核

`pip` 只安装 `playwright` 这个 Python 包，Chromium 内核需要单独下载（一百多 MB）。内核缺失时插件不会启动失败，而是在首次取数时自动执行：

```bash
python -m playwright install chromium
```

下载进度输出到 AstrBot 日志，完成后自动继续启动浏览器，无需重启插件。由「自动补装内核」控制，默认开启。

关闭该开关、或自动下载失败时，需手工执行上述命令。Linux 上若启动报缺少系统库，再补一行：

```bash
python -m playwright install-deps chromium
```

「内核通道」填写系统浏览器（`chrome`、`edge`）时不触发自动下载，该配置项指向的是系统已安装的浏览器，`playwright install` 不负责安装它。

内核是否就绪，看 `/盯价 debug <关键词>` 的「取数」行：

```
取数      浏览器 · chrome-headless-shell（已启动）
取数      浏览器 · chrome-headless-shell（未启动，首次取数时拉起）
取数      浏览器 · chrome-headless-shell（进程已退出，下次取数时自动重启）
取数      浏览器 · chrome-headless-shell（已启动） · 已自动补装内核
```

最后一种表示该次取数前刚下载完内核。

### 为什么需要浏览器

搜索页为客户端渲染：服务端返回的 HTML 只有空骨架，商品数据由页面 JS 通过 XHR 拉取后解密、再渲染。

- 请求需要 `anti_content` 签名（606 字符），由页面 JS 现算，带时效。
- 响应体是 `rc-res-data` 网关密文（十万字符），解密器位于按需加载的 chunk 中。

签名与解密均在浏览器环境内完成。插件因此启动一个无头 Chromium 执行完整页面流程，再读取内存中解密后的对象。相比解析 HTML，该方式直接取得 `goods_id`、价格原值、销量等字段，也不受页面改版更换类名影响。

「取数方式」保持默认 `browser` 即可。`http` 为旧路线（抓取 HTML 提取 `window.rawData`），搜索页改为客户端渲染后基本取不到价，保留用于排查；`auto` 先试 `http`，取不到再转浏览器，代价是多一次请求。

### 从 v3 升级

覆盖目录后重载插件。Cookie、出口代理与已有监控项均保留。注意事项：

1. 首次取数会触发内核下载。若希望提前完成，按上文手工执行一次。
2. 新增配置项按默认值生效，旧配置文件缺少该键时不需要补写。
3. 「取数方式」可改回 `http` 或 `auto`，旧路线未删除。

## 登录拼多多

「Cookie」是唯一必填项，必须为**已登录**状态的拼多多 Cookie。缺失时搜索页只返回不含商品的空壳页。

### 面板里登录（推荐）

在管理面板里打开 **插件 → 多多盯价 → 多多盯价登录**。

那一页就是拼多多的登录页本身：插件在服务器上开一台无头 Chromium，把画面按帧截成图片推到页面上，你在图上的点击、拖动、输入都会原样转发回去。所以扫码、滑块、安全验证这些只能人来做的动作，都能像在本地浏览器里一样完成。

登录成功后，画面会盖上一张卡片：绿色对勾、「登录成功」、写入了几个字段、服务器上的浏览器是否已经关闭，卡片上可以直接「再登一次」。Cookie 已经写进设置，不用你再复制任何东西。失败也一样，红叉配一句原因，不用去翻日志。

几个要点：

- 浏览器始终跑在服务器上，Cookie 只落在服务器，不经过你的浏览器，也不进聊天记录
- 会话有硬上限：10 分钟没弄完自动关掉（一台 Chromium 几百兆，不能养着）；拿到 Cookie 后 5 秒也会关
- 页面上方有「刷新页面」「结束会话」；需要打字时先点页面里的输入框，再在底部输入框里打字按回车
- 画面按容器等比缩放，面板多高都放得下，不用上下滚；想看大一点就把面板窗口拉高
- 画面高度按登录页实际高度撑开（上限 1200），保证整张二维码都在画面里，不用你自己滚
- 左上角那个带色点的标签就是状态：蓝色呼吸=正在登录，绿色=成功，红色=失败，灰色=还没开始
- 前提是「取数方式」为 `browser`；`http` 模式没有浏览器可用
- 群里也能用——面板本来就要登录，谁能进面板谁才能操作

面板里这一页打不开时：

| 现象                    | 含义                     | 处理                                  |
| --------------------- | ---------------------- | ----------------------------------- |
| 插件详情页没有「多多盯价登录」       | 面板版本过旧，或装完还没重载     | 升级 AstrBot 后重载插件；仍没有就退回手工复制 Cookie  |
| 页面一直「准备中…」            | 浏览器没起来                 | 看日志里的 `[pdd]`；先用 `/盯价 debug 纸巾` 验证浏览器 |
| 画面卡住不动                | 这一帧没截到                 | 点「刷新页面」；连续卡住就结束会话重开                 |
| 画面显示不全、要上下滚           | 面板把这一页塞进了比视口更高的框里      | 升级到 4.6.1 以上（高度钉死视口、图片等比缩放）；仍旧拉高面板窗口 |
| 二维码只露一半               | 登录页比画面高，码在下沿之外         | 升级到 4.6.3 以上（按页面高度撑开画面）；仍旧如此请把日志里 `[pdd]` 那几行发出来 |
| 提示「当前取数方式是 http」      | 配置里「取数方式」不是浏览器 | 改回 `browser` 后重载插件                   |

### 备选：手工复制 Cookie

面板那一页打不开时（插件页面没挂上、出口被限流），用下面的办法，效果一样，只是麻烦。

#### 手机端获取

1. 手机浏览器打开 `https://mobile.yangkeduo.com/`，登录。
2. 搜索任意词（如「纸巾」），确认商品列表正常显示。
3. 地址栏将当前网址替换为下列内容后回车，页面显示整条 Cookie：
   ```
   javascript:document.body.innerText=document.cookie
   ```
   部分浏览器会过滤 `javascript:` 前缀，可先手动输入 `java` 再粘贴其余部分。
4. 全选页面文字并复制。

#### 电脑端获取

1. 浏览器打开 `https://mobile.yangkeduo.com/`，扫码登录。
2. 按 `F12` 打开开发者工具，切至 **Network（网络）** 面板。
3. 刷新页面，点选任意一条 `mobile.yangkeduo.com` 请求。
4. 在 **Headers → Request Headers** 中找到 `Cookie:`，复制其后的整条值。

#### 粘贴

整段粘贴至「Cookie」，无需手工清理。以下形态均由插件自动处理：

- 带 `Cookie:` 或 `cookie：` 前缀
- 从开发者工具整段复制，夹带 `Host:`、`User-Agent:` 等其他请求头
- 长 Cookie 被折成多行
- 首尾带引号或分号

验证方法：执行 `/盯价 debug 纸巾`，输出中有一行

```
cookie    218 字符 · 11 个字段 · 含 PDDAccessToken
```

显示 `缺 PDDAccessToken` 表示复制的不是登录态 Cookie（通常为未登录时的匿名 Cookie），重新登录后再取一次。

#### 账号要求

- **使用日常在用的主号。** 风控按账号计算，新注册小号、长期不登录的号，搜索页通常直接返回「系统繁忙」。
- Cookie 等同于账号登录凭证，不应粘贴到聊天、截图或公开仓库。插件只将其放入请求头，不写入日志、数据文件或聊天回复。
- 换设备登录、退出登录、修改密码均会使旧 Cookie 失效。届时 `/盯价 debug` 开始报错，重新取一条即可。

## 设置项

全部设置在 **插件 → 多多盯价 → 插件配置** 里，六组分区与下面六节一一对应。本文一律用面板上显示的名字；表格里「默认」那一栏才是要填进去的值。

### 📮 账号与出口

| 设置         | 类型     | 默认 | 说明                                     |
| ---------- | ------ | -- | -------------------------------------- |
| Cookie     | string | 空  | 必填，须含 `PDDAccessToken`；用日常主号，新号易被风控     |
| User-Agent | string | 空  | 留空用内置 iPhone Safari；填取 Cookie 那台手机的 UA 最稳 |
| 出口代理       | string | 空  | `socks5h://user:pass@host:port`；部署在云服务器上必填 |

**出口代理** 留空表示直连。机房出口的信任度远低于家宽，不填通常表现为「系统繁忙」。走内网穿透时隧道类型须为 tcp，且部分服务商把明文 HTTP 拦成 501，改用 `socks5h://` 地址可绕开。生效与否看 `/盯价 debug` 的「代理」行。

**User-Agent** 留空时使用内置 iPhone Safari UA。填为取 Cookie 那台手机的 UA 与设备标识更一致，获取方法：手机浏览器访问 `javascript:document.body.innerText=navigator.userAgent`，复制整行填入。

### 🌐 取数方式

| 设置       | 类型     | 默认           | 说明                                     |
| -------- | ------ | ------------ | -------------------------------------- |
| 取数方式     | string | `browser`    | `browser` 无头 Chromium / `http` 旧路线 / `auto` |
| 先访问首页    | bool   | 开            | 取数前先访问首页，取回 `api_uid` 等设备 Cookie      |
| 传输方式     | string | `auto`       | `auto` / `curl_cffi` / `httpx`，仅 `http` 时生效 |
| 模拟指纹     | string | `safari_ios` | curl_cffi 模拟的指纹，仅 `http` 时生效          |
| 请求超时（秒）  | int    | 15           | 单次页面请求超时，仅 `http` 时生效                 |

**取数方式** 保持 `browser`。搜索页为客户端渲染，HTML 里没有数据，`http` 只能拿到空骨架，留作排查用。**先访问首页** 是「首次访问常拿到空壳」的解药，不建议关。

### 🖥 浏览器

| 设置       | 类型     | 默认 | 说明                                            |
| -------- | ------ | -- | --------------------------------------------- |
| 内核通道     | string | 空  | 留空用 `chrome-headless-shell`；填 `chromium` 用完整内核 |
| 无头运行     | bool   | 开  | 无头运行；服务器无桌面环境时保持开启                            |
| 取数超时（秒）  | int    | 45 | 打开搜索页到截获数据的总时限                                |
| 自动补装内核   | bool   | 开  | 内核缺失时自动执行 `playwright install chromium`      |
| 空闲退出（分钟） | int    | 10 | 空闲超过该分钟数即退出浏览器，归还内存；0 关闭                      |
| 单进程取数上限  | int    | 12 | 同一进程最多取数几次后重启；0 关闭                            |

**取数超时（秒）** 为打开搜索页到截获商品数据的总时限。走内网穿透时链路经家用宽带绕行，比直连慢，家中上行带宽较小时调至 60~90 更稳。超时报错会写明原因（跳登录页 / 系统繁忙 / 未截到明文）。

**空闲退出（分钟）** 与 **单进程取数上限** 是内存回收的两道闸门，机制见「内存占用」。前者按闲置时长回收，巡检间隔 30 分钟时每轮开头必然先退出再拉起，代价为单次一两秒；后者按取数次数回收，用于压住单轮内的增长。填 0 表示关闭对应闸门。

**自动补装内核** 关闭后，内核缺失时只报错不自救——请自行执行一次「浏览器内核」一节的命令。

### 🔍 取价规则

| 设置      | 类型     | 默认      | 说明                       |
| ------- | ------ | ------- | ------------------------ |
| 搜索排序    | string | `price` | `price` 升序 / `_price` 降序 |
| 标题分词匹配  | bool   | 开       | 按标题分词匹配选品；关闭则始终取最低价      |
| 参与匹配的条数 | int    | 5       | 参与比对的前 N 条商品，1~20        |

**搜索排序** 保持默认 `price`。改为 `_price`（降序）后第一页为最贵的一批商品，在其中取最小值将得到虚高的「最低价」。基准固定取综合排序，不受本项影响。

**参与匹配的条数** 只影响本地比对范围，不影响请求次数——所有候选商品都在同一次搜索响应内，取 5 条或 20 条对风控无区别。调大可能纳入价格高出较多的商品，调小可能排除真正匹配的那条。

### 📉 异常剔除

| 设置       | 类型   | 默认 | 说明                     |
| -------- | ---- | -- | ---------------------- |
| 剔除离群价    | bool | 开  | 匹配前先剔除价格离群的商品          |
| 离群严格度    | int  | 3  | 离群剔除严格程度，1~6，越小越严格    |
| 剔除闸门（%）  | int  | 30 | 价格闸门：低于中位数该百分比才允许被剔    |
| 基准校准     | bool | 开  | 用综合排序那一页作价格基准，校准升序页    |
| 基准下沿（%）  | int  | 60 | 低于基准中位数的该百分比即视为不同档商品   |
| 型号整串校验   | bool | 开  | 型号须在标题里整串命中，滤掉近似型号     |

**剔除离群价** 与 **离群严格度** 控制匹配前的初筛，见「取价规则 · 价格离群剔除」。默认值 3 只剔比中位数低一大截的条目：调至 1~2 更严格，可能连带剔除便宜的二手、拆机件；调至 5~6 更宽容，只剔差数十倍的极端项。关闭「标题分词匹配」时该层仍然生效。

**剔除闸门（%）** 是 MAD 剔除之外的比例闸门，默认 30。作用见「取价规则 · 价格离群剔除」。填 100 等于关闭该闸门、完全交给 MAD。

**基准校准** 开启后每个关键词会多取一次综合排序结果，用它校准升序页。机制见「取价规则 · 基准价与型号校验」。基准缓存 6 小时，稳态下不增加请求频率。

**基准下沿（%）** 默认 60：低于综合排序中位数六成的条目视为不同档商品。升序页本来就该比基准页便宜一截，卡太严会误伤促销；近似型号之间的区别不靠价格，靠「型号整串校验」。

**型号整串校验** 要求关键词里的型号原样出现在标题中。搜 `5070ti` 时结果里混着大量 `5070`，分词能命中一半、价格又便宜三千，只靠价格与分词必定选错。关键词不含型号时自动跳过。

### 🔔 巡检与推送

| 设置         | 类型     | 默认 | 说明                     |
| ---------- | ------ | -- | ---------------------- |
| 巡检间隔（分钟）   | int    | 30 | 巡检间隔                   |
| 史低主动推送     | bool   | 开  | 是否推送史低提醒               |
| 监控关键词上限    | int    | 50 | 最多监控的关键词数量             |
| 定时行情时间     | string | 空  | 每日自动播报时间，如 `20:00`；留空关闭 |
| 限流冷却上限（小时） | int    | 8  | 触发限流后的最长冷却时间           |

**巡检间隔（分钟）** 不建议低于 20。监控项较多时调大更稳。插件会把整轮的请求摊平到这个间隔里，而不是集中在开头几秒打完。

**监控关键词上限** 与巡检间隔共同决定风控暴露面：每轮对每个关键词发一次请求，数量越多单轮越久。

自 v4.3.0 之前的版本升级时，旧配置文件里平铺的键会在插件启动时自动搬进对应分区并落盘，不需要重新配一遍。

## 输出格式

所有回复与推送采用同一体例。

**首行**为 `【多多盯价】` + 动作，必要时以 ` · ` 追加对象或状态：

```
【多多盯价】已添加
【多多盯价】诊断 · 纸巾
【多多盯价】已删除 · 9700X
【多多盯价】未找到 · 9 · /盯价 list 查序号
```

**正文**为两列，标签按显示宽度补齐，值左对齐：

```
关键词    9600X
现价      ¥1049.00
史低      ¥1049.00 · 首次记录
```

**多条记录**（今日行情、监控列表）不使用列对齐，改为一项一行、以空格和 ` · ` 分隔：

```
1 纸巾 ¥8.79 ▼¥1.11 ★
2 蓝牙耳机 ¥11.90 ▲¥3.00 · 史低 ¥8.90
```

原因：手机 QQ 一屏只放得下二十来个汉字，补空格对齐的表格一折行就整列错位，对齐越整齐越难读。一项一行时，折行只影响该项自身，后续各项仍从新行开始。关键词较长的项（如 `RTX5070ti 显卡`）会折成两行，属预期行为。同理，所有汇总信息（统计、图例、提示）各自独立成行，不并排堆叠。

**错误**统一为三段，用 `｜` 分隔：现象、原因、处理。诊断输出中会拆成三行显示。

```
搜到 0 条商品｜store.data.ssrListData.list 为空｜只留型号重试：/盯价 debug 5070ti
```

不带数据的回执为单行 `【多多盯价】动作 · 对象`。

## 取价规则

### 一、监控对象是关键词

插件不识别商品链接，只识别关键词。监控的是「该关键词当前的价格」，不是某一件具体商品；同一个关键词今天的最低价可能来自 A 店，明天来自 B 店。

需锁定某一件商品时，将标题中最有辨识度的部分作为关键词（如 `AMD 9700X 盒装`），越具体越准。

关键词中的空格表示「同时包含」：`rx7800xt 花嫁` 要求标题中同时出现 `rx7800xt` 与 `花嫁`。词越多越准，但也越容易搜不到——卖家标题不一定写全系列名、后缀、缩写。典型搜不到的例子：`5070ti ultra w oc`（单独一个 `w` 几乎不作为词出现在标题中）、`amd rx9070xt 氪动极光`（系列名写错则整串落空）。

空格按 `%20` 编码后发出，连续多个空白算一个。诊断的「请求」行里看到的是 `search_key=RTX5070ti%20ultra`，属正常形态——那行是给人看的地址，中文保持可读，只有空格还原成编码样子。

搜不到时 `/盯价 debug` 会说明搜到 0 条，并给出只留型号的短版本：

```
【多多盯价】诊断失败 · 5070ti ultra w oc
现象      搜到 0 条商品
原因      store.data.ssrListData.list 为空
处理      只留型号重试：/盯价 debug 5070ti
```

这与「页面能解析但没有任何列表」是两种情况：后者说明页面连列表都未下发，属 Cookie 失效或页面改版。

### 二、价格口径

取搜索页商品条目的 `price` 字段（整数分），即搜索列表显示的拼单价。

不含券。H5 搜索页不下发券后价，取得精确到手价需逐件进入商品详情页，请求量将放大数十倍。因此：

- 有店铺券、平台券的商品，实际到手价可能低于记录值
- 百亿补贴、新人价等个性化优惠不完全体现在列表价中

该偏差对所有监控项一致，不影响「较昨日涨跌」与「是否刷新史低」的判断，仅绝对值可能略高于最终支付金额。

### 三、价格离群剔除

搜索页一次返回二三十条商品，其中混有**标题同样包含该关键词、但并非同类**的条目：外设、配件、引流 SKU。

```
¥3.99    CPU 散热器 通用 硅脂 导热膏
¥19.90   AM5 扣具 底座 9700X 兼容
¥89      9700X 散热器 六热管 静音风扇
¥139     9700X 机箱 侧透 ATX 中塔
¥1109    锐龙5 7500F/9600X/9700X 选配
¥1180    AMD 锐龙7 9700X 盒装 全新 正品      ← 目标商品
¥1382    锐龙 9700X 散片 三年质保
¥1458.50 AMD 锐龙7 9700X 盒装 二手拆机
¥1580    锐龙7 9700X 主板 CPU 套装
¥1690    AMD 锐龙9 9950X 盒装
```

前四条标题中不含「配件」「兼容」等提示词（`9700X 散热器`、`9700X 机箱`），分词比对无法区分——它们与正品一样完整命中了 `9700X`。因此插件在标题匹配**之前**先做一次价格初筛，剔除明显离群的低价条目。

算法为**对数空间的中位数绝对偏差（MAD）**，只剔下限：

1. 取全部价格的中位数作为基准
2. 计算每条价格偏离中位数的幅度，再取这些幅度的中位数，作为「正常波动范围」
3. 低于 `中位数 − k × 波动范围` 的判为离群并剔除；高于中位数的一律保留

上例 10 条的中位数约 ¥1144，下限落在 ¥392：前四条被剔除，其余六条进入标题匹配。

| 设计选择      | 原因                                                                   |
| --------- | -------------------------------------------------------------------- |
| 用对数，不用原始价格 | 商品价格右偏，¥4 与 ¥3000 相差 750 倍。线性尺度下几个高价即可将阈值撑宽，结果一条低价配件都剔不掉       |
| 用 MAD，不用标准差 | 标准差受离群点影响：越离谱的点越会把阈值推开，反而剔不掉。MAD 只看「偏离中位数多远」，对少量配件混入大量正品最灵敏   |
| 用 MAD，不用 IQR | IQR 的价格窗口在跨度大时过宽（1.5 倍 IQR 实测一条都剔不掉），不适用此场景                        |
| 只剔下限，不剔上限 | 目标是取最低价，贵的（套装、多件装）不影响结果，剔除反而误伤。单边剔除也避开了「配件多于正品时把少量正品当离群」这一误判 |

两道保护：**样本少于 6 条**不做剔除（统计量不可靠）；**剔除后剩余不足 15%** 视为剔除过度，放弃剔除、按原样处理。

`/盯价 debug` 中对应「过滤」行：

```
过滤      剔除 4 条低价离群 · 保留 6/10 · 下限 ¥392.47
```

无可剔条目时显示「价格分布连续，没有可剔除的离群项」；样本不足时显示「仅 N 条，样本太少不做剔除」。

#### 比例闸门

仅靠 MAD 存在误伤，且误伤隐蔽。实测搜索「9600X」返回 20 条，其中 18 条为「CPU + 主板」套装，集中在 ¥1645～1899：

```
¥1049    【AMD】锐龙5 9600X盒装 全新未拆封        ← 裸 CPU，目标商品
¥1459    【AMD】9000系新品 9600X 9700X 盒装
¥1479    【AMD】9000系新品 9600X 9700X 盒装
¥1549    AMD 9600X散片 搭 微星 PRO B650M-P
¥1645    【七彩虹】B850M GAMING FROZEN + AMD 96...
   ...   其后全为同类套装，直至 ¥1899
```

套装价格集中，MAD 算出的波动范围极小，下限贴至 ¥1570——**¥1049 的裸 CPU 反而成为统计学意义上的离群值**被剔除，输出的「最低价」变为 ¥1645，而实际存在 ¥1049。

因此剔除条件增加一道闸门：**仅当价格低于「中位数 × 30%」时才允许被剔**。

- ¥3.99 的导热膏 vs 中位数 ¥1144：占 0.3%，剔除
- ¥1049 的裸 CPU vs 中位数 ¥1800：占 58%，保留

闸门由「剔除闸门（%）」控制，默认 30。填 50 会将上述 ¥1049 一并剔除；填 5 更严格，仅剔差 20 倍以上者；填 100 等于关闭闸门。

严格程度由「离群严格度」与「剔除闸门（%）」控制，默认 3 与 30，均不影响请求次数，只改本地阈值。

### 四、基准价与型号校验

上面那套在**同一页内部**剔离群。有些场景单页根本看不出谁离群，因为整页都是便宜货：

```
搜「5070ti」，价格升序第一页：
¥7999    铭瑄 RTX5070 12G 终结者
¥8099    耕升 RTX5070 12G 追风
¥8249    映众 RTX5070 12G 曜夜
¥8499    技嘉 RTX5070 12G 风魔
```

真实的 5070ti 在 ¥10500～¥12500，而升序页被更便宜的 5070 占满——页内中位数就在八千，MAD 算不出任何离群项，最后记成 ¥7999。

因此插件改成**两段式**：先取一页**综合排序**当尺子，再取一页**价格升序**当候选。

| 页面     | 作用     | 为什么用它                                        |
| ------ | ------ | -------------------------------------------- |
| 综合排序   | 定基准价   | 拼多多自己的推荐排序，相关性权重高，混进来的近似型号少，价格落在真实档位         |
| 价格升序   | 找最低价   | 最便宜的一批在这里，但它会被更便宜的近似型号占满，不能单独作为判断依据          |

基准取这一页价格的中位数，下沿取中位数的「基准下沿（%）」（默认 60%）。升序页里低于下沿的条目在此出局——挂着型号名的支架、散热器、引流 SKU 都在这一步被拦下。

第二道是**型号整串校验**（设置项「型号整串校验」）。价格拦不住 5070，只有型号能：

| 关键词     | 标题                        | 结果   |
| ------- | ------------------------- | ---- |
| `5070ti` | 盈通 RTX5070Ti 16G 破茧 花嫁   | 命中   |
| `5070ti` | 七彩虹 RTX 5070 Ti 16G 战斧    | 命中   |
| `5070ti` | 铭瑄 RTX5070 12G 终结者        | 剔除   |

比对前抹平空格与 `-` `/` 等分隔符，所以「RTX 5070 Ti」与「5070ti」视为一致。型号词取关键词里最长的一段 3～5 位数字串（可带字母后缀），`16g`、`d5` 这类规格不算型号；关键词里没有型号（如「纸巾」）时自动跳过这一步。

三道筛完仍为空时，插件改用基准页本身出价——那里至少是相关商品，价格也落在真实档位。`/盯价 debug` 的「过滤」行会写明「升序页没有可用商品，改用综合排序那一页」。

**请求成本**：基准会缓存 6 小时。稳态下巡检仍是每个关键词一次请求，只有过期那一轮多打一次；新增关键词时的那次取数本来就要算基准，结果顺手存下，不额外花请求。

```
基准      综合排序 20 条 · 中位 ¥11748.04 · 缓存 2 小时前
过滤      剔除 12 条低于基准 · 保留 8/20 · 下沿 ¥7048.83
型号      5070ti · 剔除 3 条不含该型号的
```

关掉「基准校准」即退回单页 MAD 模式；关掉「剔除离群价」则连基准也不再取，价格完全不筛。

### 五、标题匹配

初筛后的商品基本属同一品类，但品类内部仍有差别：选配 SKU、散片、二手、拆机，价格可相差数成。此步按标题分词比对，选出与关键词最接近的一条。

1. 关键词分词，得到关键词词集
2. 取价格最低的前 N 条（「参与匹配的条数」），标题各自分词
3. 计算重合度 = 交集词数 ÷ 关键词词数
4. 标题含「配件」「兼容」「选配」等词、而关键词本身不含时，重合度对折（降权）
5. 取分值最高者作为价格参考
6. 次低取其后的两条

上例中关键词 `AMD 9700X 盒装` 切为 `{amd, 9700x, 盒装}`，剔除离群后剩六条，取前 5 条比对：

| 商品                        | 交集          | 重合度        | 降权后         |
| ------------------------- | ----------- | ---------- | ----------- |
| 锐龙5 7500F/9600X/9700X 选配  | 9700x       | 33%        | 17%（选配）     |
| **AMD 锐龙7 9700X 盒装 全新 正品** | amd、9700x、盒装 | **100%**   | **100%** ← 选中 |
| 锐龙 9700X 散片 三年质保          | 9700x       | 33%        | 33%         |
| AMD 锐龙7 9700X 盒装 二手拆机     | amd、9700x、盒装 | 100%（同分，更贵） | 100%        |
| 锐龙7 9700X 主板 CPU 套装       | 9700x       | 33%        | 33%         |

结果为底价 ¥1180，次低 ¥1382、¥1458.50。

规则细节：

- **平局**：分值相同则命中词更多的优先，仍相同则取价格更低者
- **型号不切碎**：jieba 会把 `9700X` 切成 `9700` + `X`，插件另以正则将型号整串补入词集，因此 `9700X` 命中 3 个词、`9700K` 只命中 1 个，不会互相混淆
- **降权不改展示分**：`/盯价 debug` 显示原始重合度，另标「含配件词已降权」
- **兜底**：前 N 条均未命中关键词、或关键词无法分出有效词（如仅填标点）时，退回取最低价，不报错
- **无 jieba**：退化为子串匹配，`/盯价 debug` 中标注「子串匹配」

## 浏览器环境

TLS、HTTP/2、JS 引擎、Canvas、字体、触摸支持均由 Chromium 自身生成，无需另行构造指纹。插件额外处理两项：

- 关闭 `AutomationControlled` 特征，并将 `navigator.webdriver` 置为 `undefined`（无头浏览器最易被识别的标记）
- 使用 iPhone UA + 440×956 视口 + `is_mobile`，三者须同时设置。缺一项即落入「系统繁忙」——桌面 UA 访问移动站是该页面最典型的拒绝方式

`curl_cffi` 仍保留在依赖中，仅在「取数方式」为 `http` 时使用（该路线基本取不到价，保留用于排查与应急）。

「User-Agent」留空时使用内置 iPhone Safari UA。填为取 Cookie 那台手机的 UA 与设备标识更一致，获取方法：手机浏览器访问 `javascript:document.body.innerText=navigator.userAgent`，复制整行填入。

> 上述手段只降低概率。平台风控同时考察账号活跃度、历史行为、IP 归属，插件无法干预。**使用日常在用的主号，比任何指纹伪装都有效。**

## 内存占用

### 不归还的原因

Chromium 的内存行为与常规进程不同：关闭 page、关闭 browser context 都不会把内存还给操作系统。渲染进程退出后 V8 堆、网络缓存、私有页仍被浏览器主进程持有，复用到下一次，看起来像「只涨不降」。只有**浏览器进程本身退出**，这部分内存才被全额回收。

插件因此不靠「关页面」省内存，而是让进程周期性退出。

### 三道约束

| 手段                          | 作用                                                     |
| --------------------------- | ------------------------------------------------------ |
| 空闲退出（分钟） | 最后一次取数后闲置超过该时长，整个浏览器退出。巡检间隔 30 分钟时每轮开头必触发一次                |
| 单进程取数上限 | 同一进程累计取数达该次数即重启。监控项多时单轮内会连着取十几次，此闸门用于压住单轮内的增长        |
| 启动参数                        | 限制渲染进程数、V8 堆上限、关闭 GPU 与后台网络，降低峰值                       |

启动参数为：

```
--renderer-process-limit=1          单页场景，避免每个 iframe 各起一个渲染进程
--js-flags=--max-old-space-size=512 给 V8 堆封顶；默认上限按物理内存推算，小内存机器会越吃越多
--disable-gpu                       无头取数用不到 GPU，省掉显存与共享内存映射
--disk-cache-size=1048576           磁盘缓存压到 1 MB；每次都是同一个搜索页，缓不缓存无差别
--disable-background-networking     关掉组件更新、翻译、同步等后台请求
```

回收状态在 `/盯价 debug` 的「内存」一行：

```
内存      已取数 3/12 次 · 回收 2 次 · 空闲 10 分钟退出
```

`已取数 N/M` 为当前进程实例已取数次数与阈值，`回收 N 次` 为插件启动以来的累计回收次数。后者随巡检推进而增长是正常的，说明回收在生效；一直为 0 则说明从未触发过，需检查两个闸门是否被填成了 0。

### 曲线判读

监控内存时先看形状：

- **阶梯式**——每次巡检抬升一级，随后长时间走平。这是常态：每轮取数把内存推到新一级，回收后本该回落，若回收阈值设得过大就会停在峰值。见此形状先确认 `/盯价 debug` 的回收次数是否在涨。
- **持续斜线**——没有平台期，一小时内稳定上行。这不是 Chromium 的常规行为，优先怀疑别处：日志文件、会话数据累积，或同机其他进程。
- **单次尖峰后不回落**——某轮巡检后内存永久抬高一个台阶，且回收次数不涨。多半是回收时进程没退干净，或浏览器在该轮被杀后留下了孤儿进程。

确认插件实际占用：

```bash
ps -eo rss,args | awk '/chrom|headless_shell/ && !/awk/ {s+=$1} END {printf "%.0f MB\n", s/1024}'
```

该数值为所有 Chromium 相关进程的常驻内存合计。回收生效时应看到它周期性归零再重新爬升；若长时间只增不减且 `/盯价 debug` 的回收次数同步增长，说明有进程未被回收，用 `ps -ef | grep headless_shell` 查看是否有多个主进程并存。

### SOCKS5 中继

`socks5h://` 代理由插件在本地起一个中继线程转发——Chromium 不支持 SOCKS5 用户名密码认证，需本地中继代为握手。每次启动浏览器建立一个新中继（新线程、新随机端口），因此**回收浏览器时必须同时收掉中继**，否则每回收一次漏一个线程和一个监听端口。该释放已与浏览器关闭绑定，随 `_shutdown_pw()` 一同执行。

## 出口 IP

**症状**：同一账号在本机浏览器中可正常搜索，但部署在阿里云、腾讯云等机房的机器人始终返回「系统繁忙」降级页。Cookie 完整，指纹已伪装，仍无效。

**原因**：平台除账号与指纹外，还判断请求来源 IP 段。机房 IP 归属为云厂商 ASN，天然带「服务器」标签，而爬虫绝大多数运行在云端。家用宽带、手机流量为住宅 ASN，信任度不同。**此类拒绝不是封号，等待不会恢复，换账号亦无效——变的是 IP，不是身份。**

判断方法：确认浏览器与机器人是否使用同一出口 IP。不同则优先怀疑该层。

**解法**：为「出口代理」填入住宅出口。

```
http://host:port
http://user:pass@host:port
socks5h://user:pass@host:port    # 走内网穿透时优先
socks5://user:pass@host:port     # 域名在客户端先解析为 IP 再发往代理
```

`socks5h` 与 `socks5` 的区别仅在**由谁做 DNS**：

- `socks5h://` —— 域名原样送至代理端，由代理解析。**优先使用**：出口 IP 与 DNS 均来自同一条家宽，结果与真实浏览器一致，也可避免客户端解析到 IPv6 而代理不通。
- `socks5://` —— 客户端先将域名解析为 IP，再以 IP 形式发往代理（常见为 IPv6）。自建代理若限制 IP 直连，会在此被拒。

来源按可行性排序：

1. **自有家宽**——路由器端口映射，或在局域网运行 HTTP 代理（`tinyproxy`、`squid`）后映射出去。免费且为真实家宽 ASN，最稳。
2. **手机热点 / 随身 WiFi**——同理，走移动网络 ASN。
3. **住宅代理服务**——按流量计费，选择国内住宅 IP，注意合规与稳定性。

### 内网穿透的三个问题

**其一：隧道类型须为 `tcp`。** `http` 类型隧道为虚拟主机模式，按 `Host` 路由，只接受 `GET`/`POST`，代理的 `CONNECT` 请求会被回 `501`。

**其二：部分服务商对隧道做 HTTP 内容合规检测，会拦截明文 HTTP 流量。** 隧道日志显示「TCP 隧道启动成功」，但客户端收到的是服务商错误页：

```
HTTP/1.1 501 Not Implemented
Server: SakuraFrp
```

页面正文提示「您正试图使用 HTTP 协议访问此隧道……请启用 HTTPS 后访问」。此时更换隧道类型、线路、端口均无效，因为拦截依据是**协议**而非隧道配置。

**解法：改用 SOCKS5。** SOCKS5 握手为二进制（`\x05\x01\x00`），不构成 HTTP 请求，不被此类规则命中。将代理端点改为 SOCKS5 后：

```
socks5h://user:pass@节点域名:远程端口
```

应写 `socks5h` 而非 `socks5`。`socks5://` 会让客户端先解析域名，若解析到 IPv6 而代理只监听 IPv4 出口，会在握手末步被拒。`socks5h://` 交由代理端解析，绕开此类问题。

自建代理时同时监听 HTTP 与 SOCKS5 最省事：按首字节 `0x05` 分流即可。

**其三：Chromium 不发送 SOCKS5 用户名密码。** Chromium 的 SOCKS5 握手只声明「免认证」（`0x00`），`socks5://user:pass@host:port` 中的账号密码不会发送；而暴露至公网的代理为安全起见必须带认证，两者不匹配，连接直接失败。

插件已做处理：「出口代理」里带密码时，插件在本机 `127.0.0.1` 启动一个免认证的 SOCKS5 端口，由其携带账号密码连接上游并双向转发。

```
Chromium → 127.0.0.1:随机端口（免认证）→ 本地中继（带认证）→ 隧道 → 上游代理
```

由此可得：

- **不需要**为迁就浏览器将公网代理改为免认证，密码保留；
- 中继只监听回环地址，局域网内其他机器无法连接。上游的域名白名单、端口白名单、内网地址拦截照常生效——中继只代为认证，未放宽任何目标侧限制。

配置完成后执行 `/盯价 debug <关键词>`，「代理」行显示脱敏后的地址：

```
代理      socks5h://pdd:***@frp-van.com:11428
```

该行出现即表示请求确实经代理发出。代理不通时插件会报「网络请求失败」，不会静默直连。

## 故障排查

单个关键词取不到价时执行：

```

```

输出共 12 行左右，按行判读：

| 行      | 判读                                                                 |
| ------ | ------------------------------------------------------------------ |
| `命中`   | 搜索返回的商品条数。为 0 见下文「搜到 0 条」                                         |
| `基准`   | 综合排序那一页的条数、中位价、是刚取还是缓存。价格明显不对时先看这行                            |

| `型号`   | 型号整串校验：命中的型号词与剔掉的条数。没有这一行说明关键词不含型号                            |

| `请求`   | 仅在失败时出现，为实际发出的地址，空格以 `%20` 呈现                                     |

失败时首行为 `诊断失败`，`现象`、`原因`、`处理`三行给出结论：

| 现象                         | 原因               | 处理                                     |
| -------------------------- | ---------------- | -------------------------------------- |
| `跳登录页`                     | Cookie 缺失或已失效    | 到面板「多多盯价登录」扫一次，或按上文手工复制 Cookie          |
| `页面报「系统繁忙」且未截到任何数据包`       | 出口 IP 被限流，或代理未生效 | 查看「代理」行确认生效；仍如此则更换出口                   |
| `页面报「系统繁忙」，但已截到数据包`        | 偶发限流             | 重试一次                                   |
| `没装 playwright`            | 依赖未装             | `pip install playwright`               |
| `内核下载失败` / `内核下载超时`         | 网络或磁盘问题          | 按提示手工执行 `python -m playwright install chromium` |
| `内核下载完仍启动失败`               | 缺系统库             | `python -m playwright install-deps chromium` |
| `页面渲染出 N 个价格，hook 未截到明文`   | 数据不再经 `JSON.parse` | 上报此条等待适配；临时把「取数方式」改成 `http`        |
| `搜到 0 条商品`                 | 该关键词确实无结果        | 按「处理」只留型号，如 `5070ti`                   |
| `搜到 N 件商品，没有一件能解析出价格`     | 价格字段改名           | 上报此条等待适配                               |
| `搜索页正文为空`                  | 页面壳没渲染，多为首次访问缺设备 cookie | 插件已自动重试一次；连续如此检查「先访问首页」、Cookie 与出口 |
| `页面能解析但没有任何列表`            | Cookie 失效或页面改版    | 重新取 Cookie；仍报错则上报                       |

判据：报错带 `store.data.ssrListData.list 为空` 说明结构未变、该页无商品；带「首条字段：xxx」为改版；带「系统繁忙」为平台拒绝。

`搜到 0 条商品` 最常见，多为关键词过长或型号写错。换成「纸巾」重试：能出价说明插件与 Cookie 均正常，是该词本身无结果。

面板登录失败时（先在日志里找 `[pdd]` 开头的几行，那几句写明了卡在哪一步）：

| 现象                    | 含义                     | 处理                                |
| --------------------- | ---------------------- | --------------------------------- |
| 页面一直「准备中…」           | 浏览器没起来                 | 看日志里的 `[pdd]`；先用 `/盯价 debug 纸巾` 验证浏览器 |
| 回执 `打开登录页失败`         | 出口不通或被拦                | 看 `/盯价 debug` 的「代理」行，与取数失败同一套判断  |
| 回执 `没有浏览器可用`         | 「取数方式」不是 `browser`      | 改回 `browser` 后重载插件                |
| 二维码只露一半              | 登录页比画面高，码在下沿之外         | 4.6.3 起会按页面高度撑开画面；仍旧如此把 `[pdd]` 日志发出来 |
| 日志 `画面里没找到二维码元素`     | 三层兜底都没命中，页面结构又变了       | 把日志、以及截图发一版给作者，改成新选择器             |

### 同一个词 add 报无价、debug 有价

同一条取数路径，正常情况下两次结果一致。历史上出现差异有两个原因，均已处理：

- **首页预热只覆盖 HTTP 路线**。浏览器路线直接打开搜索页，首个页面常常只返回一个不渲染的空壳（标题「拼多多」、正文空白），hook 自然截不到数据。现改为每个浏览器进程首次取数前先在同一 context 访问一次首页，取得 `api_uid` 等设备 cookie。
- **add 只试一次**。空壳多为客户端水化的时序问题，重试一次通常就出价。现在 `add` 与 `debug` 共用 `_first_price()`，非风控类失败自动重试一次，间隔 1 秒；风控类失败不重试，避免越试限得越久。代价是失败时最多取数两次，最坏等待接近两个「取数超时」。

若两者仍不一致，先看 `/盯价 debug` 的「取数」行是否显示回收中或进程已退出——回收后第一次取数要重启浏览器，耗时比平常长。

### 价格比预期低很多

先看 `/盯价 debug` 的「最低」与「商品」两行，确认拿到的是不是同一型号。

| 现象                     | 原因                        | 处理                                   |
| ---------------------- | ------------------------- | ------------------------------------ |
| 商品标题里没有关键词里的型号         | 型号校验被关掉，或型号词没提取出来         | 打开「型号整串校验」；确认关键词里有完整型号    |
| 「过滤」显示「改用综合排序那一页」      | 升序页全被更便宜的近似型号占满，只能拿基准页出价  | 正常兜底，价格来自综合排序，不是绝对最低                 |
| 「基准」中位价明显偏低            | 综合排序页本身混入了大量低价近似型号        | 把「基准下沿（%）」调高，或改用更精确的关键词 |
| 「基准」显示「综合排序样本不足」       | 那一页商品太少，算不出中位数            | 属于正常回退，走单页离群剔除                       |

### 浏览器进程退出

浏览器进程被系统回收（内存不足等）时无需干预。每轮取数前会检查进程存活状态，断开则自动重启后重试一次；仅重启失败时记为一次失败。`/盯价 debug` 的「取数」行会显示「进程已退出，下次取数时自动重启」。

### 内存持续上涨

先看曲线形状，再决定查哪里：

| 形状             | 含义          | 处理                                      |
| -------------- | ----------- | --------------------------------------- |
| 阶梯：每轮巡检抬一级后走平  | 回收阈值偏大，停在峰值 | 调小「单进程取数上限」；确认「内存」行的回收次数在增长 |
| 斜线：无平台期，稳定上行   | 不是浏览器单方面的问题 | 查日志与数据文件大小、同机其他进程；对比停用插件后的曲线            |
| 尖峰后永久抬高一级      | 回收时进程未退干净   | `ps -ef \| grep headless_shell` 看是否有多份主进程并存 |

`/盯价 debug` 的「内存」行给出当前实例已取数次数与累计回收次数。回收次数随巡检增长为正常；长期为 0 说明两个闸门被填成了 0，或回收逻辑未进入。

### 风控与退避

命中「系统繁忙」「验证码」等平台拒绝时，插件**立即中止本轮巡检**，不再请求其余关键词；`/盯价 check` 显示「中止」行。已有价格不会被清空。

「系统繁忙」有两种，处理方式相反：

| 现象                | 含义        | 处理                                        |
| ----------------- | --------- | ----------------------------------------- |
| 整页即为「系统繁忙」文字、无数据 | 账号被限流     | 等待数小时；或换号。换号立即恢复则印证为账号级                  |
| 数据仍在、商品列表为空       | 请求被识别为异常客户端 | 依次检查：指纹（取数行）、Cookie 字段（cookie 行）、出口 IP（代理行） |

第二种的典型特征为：**同一账号在浏览器中可正常搜索，仅脚本不可**。等待不会恢复，换账号亦无效——被识别的不是账号，而是该机器的请求特征。

随后进入指数退避：第 1 次冷却 1 小时，第 2 次 2 小时，第 3 次 4 小时，至「限流冷却上限（小时）」（默认 8）封顶。冷却期内不开始下一轮巡检。

连续第 2 次命中时推送：

```
【多多盯价】巡检暂停
原因      搜索页连续拒绝请求
冷却      120 分钟
恢复      /盯价 reset 立即重试
```

恢复后推送 `【多多盯价】巡检恢复 · 风控计数清零` 并清零计数。

修改配置后不愿等待冷却，执行 `/盯价 reset`：清空风控计数与冷却时间，同时清零各监控项的失败计数，随后可立即 `/盯价 debug` 验证。

> 拒绝分两个层级：**账号级**（浏览器亦不可搜索，换号或等待）与**请求特征级**（浏览器可搜、仅脚本不可，换号无效，需调整指纹或出口）。无法区分时先看「取数」「代理」两行。

## 数据与隐私

- 存储位置：`data/plugin_data/astrbot_plugin_pdd_monitor/pdd_price.json`
- 内容：监控项、每日价格快照、推送会话列表、服务端下发的设备 Cookie
- 写入方式：临时文件 + `os.replace` 原子替换
- **不存**页面原文，**不存**登录态 Cookie（`PDDAccessToken` 等三个字段始终只从配置读取）
- 唯一例外为排查用页面快照：仅在手动执行 `/盯价 debug` 且取价失败时写入 `debug/` 子目录，巡检不写。快照为完整页面源码，**不含 Cookie**，排查后可删除
- 文件带 `data_version` 字段；价格口径变更时升级版本，读到旧版本文件会清空监控与历史（保留推送会话列表）

单个监控项记录：关键词、当前最低价商品（标题 / 商品 id / 链接）、最近一次搜索的最低 3 条、现价、历史最低价及时间、每日快照、连续失败次数与最近错误。

## 已知限制

- **价格不含券**：见「取价规则 · 价格口径」。
- **监控关键词而非商品**：最低价可能来自不同店铺，史低提醒中标注商品标题与 id 便于判断。
- **仅取搜索页第一页**：30~60 条。价格升序时该页为最便宜的一批，但不是全站绝对最低价。
- **依赖 Cookie**：换账号登录、退出登录、长时间不活跃均会失效，需手动更换。
- **两层过滤均有边界**：标题匹配依赖卖家将型号写入标题（写作「处理器 8 核 全新」则无法对上）；离群剔除依赖「配件明显便宜于正品」这一前提（配件与正品同价时无法剔除）。此类关键词，写具体比调参数有效。
- **风控为账号级**：被限流后只能等待或换号，插件能做的是中止本轮并退避。
- **主动消息**：个人号 QQ（aiocqhttp）、Telegram、飞书支持主动推送；QQ 官方接口、企业微信、钉钉不支持，只能通过「今日行情」被动查询。

## 常见问题

| 现象                   | 原因与处理                                                          |
| -------------------- | -------------------------------------------------------------- |
| 提示未配置 cookie         | 插件配置中未填，填好后重载插件                                                |
| 全部关键词报「系统繁忙」         | 账号被限流。换主号，或等待数小时；退避机制会自动恢复                                     |
| 全部关键词报「跳登录页」         | Cookie 失效或为未登录 Cookie，重新取一条                                     |
| 换账号后立即恢复             | 印证限流为账号级，非插件问题                                                 |
| 某个关键词一直搜不到商品         | 该词本身无结果。换成「纸巾」验证插件是否正常                                         |
| 记下的价格明显偏低（似配件价）      | 查看 `/盯价 debug` 的「过滤」行：未剔离群项时将「离群严格度」调至 2；再查看「匹配」行，将「参与匹配的条数」调大或换更具体的词 |
| `/盯价 debug` 显示「子串匹配」 | 未装 jieba，`pip install jieba` 后重启                                |
| 价格比 App 中略高          | 列表价不含券，App 中可能叠加店铺券或补贴                                         |
| 价格小幅频繁跳动             | 搜索结果的商品集合本身在变化，最低价来自不同店铺，属正常现象                                 |
| 群内收不到史低推送            | 群内执行一次 `/盯价 on`；或该平台不支持主动消息                                    |
| 更新插件后数据丢失            | 价格口径变更导致 `data_version` 升级，旧数据被清空属预期行为                          |
| Cookie 疑似泄露          | 在拼多多 App 退出登录后重新登录，旧 Cookie 立即失效                                |

## 与对话上下文的关系

- 不调用 LLM 接口，不消耗 token，不写入会话历史。
- 指令回复与史低推送为平台层消息，不进入 AstrBot 会话上下文。
- 「今日行情」监听器仅在短问句命中时接管消息，其余放行给 LLM：
  - `今日行情`、`@机器人 今天行情` → 接管
  - `帮我把今日行情做成表格` → 放行（剥离触发词后超过 6 字）
  - 群内未 @机器人 → 不接管
- 已识别插件自身消息（以 `【多多盯价】` 开头），避免平台回显导致自问自答。
